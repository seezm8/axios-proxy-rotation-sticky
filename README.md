# axios proxy: a working Node.js setup with rotation, sticky sessions and the errors decoded

Search for "axios proxy" and you'll get two completely different problems wearing the same name. One is a frontend dev-server trick for dodging CORS during local development. The other is a real forward proxy that hides your server's IP while it scrapes. Half the tutorials mix them up, which is why people copy a config block, get a `407`, and start blaming Axios.

Here's the version that holds up in production: how axios resolves proxies, which method to use for HTTPS and auth, how to rotate IPs without rewriting your request code, and where DataImpulse's gateway fits in.

## Two problems, same search term

**The dev-server proxy.** In a Vite or webpack project you write `axios.get('/api/products')` and let the dev server forward `/api` to `https://api.example.com`. That's a proxy, but only inside your dev environment. It dies the moment you ship, and it does nothing for anonymity. If this is what you need, stop reading vendor guides and look up your bundler's `server.proxy` or `proxyTable` config.

**The forward proxy.** Axios opens a tunnel through a proxy server before reaching the target. This is what you need for scraping, price monitoring, ad verification, or checking how a page looks from another country. Everything below is about this case.

One thing worth knowing early: in the browser, axios cannot set a proxy in code. Browsers don't expose proxy configuration to JavaScript. If your requests live in client-side code, the proxy has to come from the browser settings or an extension — the same axios config that works in Node.js will be silently ignored.

## Four ways to route axios through a proxy

| Method | HTTPS targets | Proxy auth | Per-request control | Suits rotation | Setup |
| --- | --- | --- | --- | --- | --- |
| Inline `proxy` option | Works on current Axios versions, historically flaky | Yes (`auth` object or URL credentials) | Yes | No | Low |
| `axios.create()` defaults | Same as above | Yes | Instance-wide only | No | Low |
| `HTTP_PROXY` / `HTTPS_PROXY` env vars | Yes | Yes, via credentials in the URL | No | No | Low |
| `httpAgent` / `httpsAgent` via a proxy agent | Yes, and it's the only path for SOCKS | Yes | Yes | Yes | Medium |

Axios resolves `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` itself through `proxy-from-env`, so the env-var route works without extra packages. Newer Node releases (24.x, with the flag backported to 22.21+) also ship a native env-proxy mode via `NODE_USE_ENV_PROXY=1`. Pick one mechanism and stay with it — running Axios's own resolution on top of Node's native mode is a popular way to spend an afternoon debugging routing you can't explain.

## The setup most scrapers end up using

The built-in `proxy` option handles a single, unchanging proxy fine. It becomes awkward the moment you need a per-request agent, SOCKS5, or an IP pool. The agent pattern covers all three:

js
// npm i axios https-proxy-agent
const axios = require('axios');
const { HttpsProxyAgent } = require('https-proxy-agent');

const proxyUrl = 'http://LOGIN:PASSWORD@gw.dataimpulse.com:823';
const agent = new HttpsProxyAgent(proxyUrl);

const client = axios.create({
  httpsAgent: agent,
  proxy: false,        // stop axios from doing its own proxy resolution
  timeout: 15_000,
});

const res = await client.get('https://httpbin.org/ip');
console.log(res.data); // this should show the proxy IP, not your server's


`proxy: false` is the line people forget. Without it, Axios may apply its own proxy handling on top of the agent you just passed, and you get a request that looks configured but egresses from the wrong place. Verifying with an IP-echo endpoint after every config change is cheap insurance.

### Credentials: where 407 really comes from

Proxy auth goes in the URL (`http://user:pass@host:port`) or in the agent's options. If your password contains `@`, `:` or `/`, dropping it into a URL unencoded breaks parsing — and the resulting `407 Proxy Authentication Required` looks exactly like a wrong-password error. Percent-encode it, or pass credentials as a separate option rather than inside the string.

For HTTPS targets the credentials travel in a `Proxy-Authorization: Basic` header generated by the agent. That's the same mechanism behind a class of bugs where requests fail only for certain accounts: the header has to use standard base64, and anything producing a URL-safe base64 output gets rejected by a strict proxy. If a proxy works from `curl` and fails from a JS runtime, that's the first thing to check.

## Rotation and sticky sessions without touching call sites

DataImpulse runs a single rotating gateway at `gw.dataimpulse.com` — HTTP on port 823, SOCKS5 on port 824 — so a new IP on the next request is the default behaviour. No proxy list to maintain.

Sessions and geo-targeting ride inside the username, which means they're set per request rather than per account:

js
// country only — country targeting is included in the price
'http://LOGIN__cr.us:PASSWORD@gw.dataimpulse.com:823'

// country + city + a named sticky session held for 600 seconds
'http://LOGIN__cr.us;ci.newyork;sid.job01;sessttl.600:PASSWORD@gw.dataimpulse.com:823'


That naming matters in practice. Shopping carts, login flows and paginated listings break if the exit IP changes between requests, so you want `sid` plus a TTL for those, and a fresh rotating connection for bulk fetches. A request interceptor is the clean place to decide:

js
const pool = [ /* rotating agent, sticky agent A, sticky agent B */ ];

client.interceptors.request.use((config) => {
  config.proxy = false;
  config.httpsAgent = pickAgentFor(config.url);
  return config;
});


Request interceptors run last-in-first-out in Axios, so if you also add auth headers or logging interceptors, the order you register them is the reverse of the order they run. Response interceptors go the other way, first-in-first-out. This trips up more people than the proxy config itself.

## Retries that don't duplicate your POSTs

Blind retries against a rotating pool are how one bad request becomes a loop of duplicate writes. Bound the retry, and only for replay-safe methods:

js
client.interceptors.response.use(undefined, async (error) => {
  const config = error.config;
  if (!config) throw error;
  const method = String(config.method ?? 'get').toUpperCase();
  config.__retry ??= 0;
  if (method !== 'GET' || config.__retry >= 1) throw error;
  config.__retry += 1;
  config.httpsAgent = differentAgent(); // new exit IP for the second attempt
  return client.request(config);
});


A `429` or `403` on the first try usually means the target doesn't like that IP or that country. Changing the exit IP once and giving up is a reasonable policy; hammering the same host from a hundred IPs is how accounts and access get shut down instead of just rate-limited.

## SOCKS5

Axios's built-in option is HTTP/HTTPS-only. SOCKS support comes from an agent:

js
// npm i socks-proxy-agent
const { SocksProxyAgent } = require('socks-proxy-agent');
const agent = new SocksProxyAgent('socks5://LOGIN:PASSWORD@gw.dataimpulse.com:824');

await client.get('https://httpbin.org/ip', { httpsAgent: agent, proxy: false });


SOCKS5 forwards any TCP traffic rather than understanding HTTP, so it's the fallback when a target behaves oddly through an HTTP proxy. It solves nothing about detection on its own — the IP reputation is still what the target sees.

## The errors you'll actually hit

| Symptom | Usual cause | What to check first |
| --- | --- | --- |
| `407 Proxy Authentication Required` | Missing, malformed or unencoded credentials | Encode special characters; confirm login and password are the proxy ones, not your dashboard email |
| `ECONNREFUSED` | Wrong host/port, or proxy unreachable | `curl -x http://host:port https://ipinfo.io` before touching the axios config |
| `ETIMEDOUT` | Timeout too tight, or the exit IP is dead | Measure where the time goes; swap the route rather than raising the timeout forever |
| `ECONNRESET` mid-response | Connection dropped at the proxy or origin | Retry only replay-safe requests |
| Response shows your own IP | `proxy: false` with no agent, or `NO_PROXY` matching the host | Check every layer that could be claiming routing, including env vars |
| `401`/`403` from the target | The target rejected the IP or the request shape | Try one different country or session; don't treat a new IP as permission |

## When axios isn't the answer

Two cases where changing the proxy config won't help. If the data you need only appears after JavaScript executes, an HTTP client gets the shell of the page regardless of how good your IP is — that's a browser automation problem, not a proxy problem. And if the requests originate in client-side code, the browser, not Axios, owns proxy routing.

Everything else — API collection, price monitoring, geo-checked content, bulk fetches behind a rotating pool — is a solved pattern: an agent, `proxy: false`, credentials in the URL, sticky sessions where state matters, and a bounded retry on GETs.

That's the whole setup. The tutorials that make it look complicated are usually the ones selling you a proxy list you don't need.
